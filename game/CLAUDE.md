# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this project is

Ascendant Impact is an Unreal Engine **5.8** PC project, **Blueprint-only** — there is no `Source/` folder, no C++ build, and no traditional lint/test commands. All implementation lives in binary `.uasset`/`.umap` files under `Content/`.

Scope is a single-duel prototype: the player (Echo or Nova) fights Crimson Vanguard, who uses authored, deterministic AI. Design/planning source of truth is the separate `fight-game` repository (locally at `C:\Users\Tonys ProArt\Documents\fight-game`); this repo is the Unreal implementation only.

## Operating rules (from AGENTS.md — binding)

- Blueprint-first; do not add C++ without approval.
- Do not directly edit binary Unreal assets on the filesystem, and never import assets or install plugins/frameworks without explicit human approval.
- Only Attack A is enabled until its complete loop passes; Attacks B–D stay planned and disabled. No runtime LLM/generative-NPC behavior. No scope beyond the single-duel prototype (no PvP, multiplayer, extra fighters/arenas, progression).
- Report planned changes before modifying project architecture.
- Never commit `Binaries/`, `DerivedDataCache/`, `Intermediate/`, `Saved/`, `.vs/`, or plugin-local generated folders (already in `.gitignore`).

## How to work on this project

All editing happens through the **unreal-mcp** MCP server against the live editor session (the editor must be open). Start with `mcp__unreal-mcp__list_toolsets`, then `describe_toolset` for schemas, then `call_tool`. Key toolsets:

- `editor_toolset.toolsets.blueprint.BlueprintTools` — Blueprint graph editing (DSL read/write, nodes, variables, compile).
- `editor_toolset.toolsets.object.ObjectTools` — **always** `list_properties` before `get/set_properties`; property names cannot be guessed and wrong names fail silently.
- `editor_toolset.toolsets.scene.SceneTools`, `asset.AssetTools`, `data_table.DataTableTools`, `UMGToolSet` — level, assets, DataTables, widgets.
- `EditorToolset.EditorAppToolset` — PIE start/stop, viewport capture, selection.
- `AutomationTestToolset` — the closest thing to a test runner: `DiscoverTests()` → `ListTests()` → `RunTests()` → `GetTestResults()`.

Validation standard: `compile_blueprint(warnings_as_errors=true)` must come back clean after every Blueprint change, then save the asset via MCP. There is no MCP asset-validation tool; suggest the human run **Tools → Validate Assets** for final sign-off. Functional verification is a human PIE pass — write test instructions rather than assuming success.

### Known tooling gotchas (hard-won; see docs/agent/PROTOTYPE_BLACKBOARD.md §6 and §11.9 for detail)

- **Git**: `.git` is owned by a different Windows user; every git command must be invoked as `git -c safe.directory="E:/UnrealProjects/Production/AscendantImpact" ...` (do not modify global git config).
- **OFPA level saves**: levels use One-File-Per-Actor. Newly placed actors in an existing level could not be saved via `save_actor` ("Asset does not exist" — human Ctrl+S was the workaround; on the next occurrence try `save_assets([])` first). However (confirmed 2026-08-02): `AssetTools.duplicate` + `save_assets` persists an entire level copy including all external actor packages, and **`save_assets([])` (empty list = save all dirty) flushes OFPA actor deletions and modifications to disk** — a map-path-only save does not. Verify persistence with a `load_level` round-trip.
- **Stale per-instance component data**: actors placed in the level *before* a component was added/configured on their Blueprint class keep a frozen snapshot that overrides both `set_properties` and `reset_properties`. Fix by deleting and re-placing the instance.
- **Blueprint DSL quirks**: `(event ...)` sugar can't create Enhanced-Input events or match existing custom events — place nodes with `add_event`/`create_node` (find real type ids via `find_node_types`) and wire with `connect_pins`. Function graphs cannot contain latent nodes (`Delay`); use event-graph contexts. Array input pins reject literal defaults — feed them a `MakeArray` node. Bool variables drop the `b` prefix in accessor names (`bIsAttacking` → `Get/SetIsAttacking`), and variable accessor type ids include the variable's category (`Variables|DuelCamera|GetDuelModeActive`, not `Variables|Default|…`). `SpawnActorFromClass`'s `SpawnTransform` by-ref pin also rejects literal defaults — wire a `MakeTransform` node. Type ids containing parentheses (`Math|Float|Clamp(Float)`) break the S-expression parser — use `select` ternaries / component math instead. Own-function calls need keyword args (`:Param val`) or positional args may bind to `self` — the same applies to any node whose first data pin is `self` (e.g. `Rendering|SetActorHiddenInGame :bNewHidden`), where a positional bool binds silently to `self` and the call no-ops. `get_node_type_pins` instantiates a probe node in the graph — delete it afterward. Paren-containing type ids (`Math|Float|Max(Float)`, `Utilities|String|ToString(Float)`) DO parse in the DSL. `Utilities|Array|MakeArray` cannot be typed from DSL for enum-array pins — create it with `create_node`, connect to the array pin (wildcard resolves), then set the element value. A compile immediately after graph surgery in the same ProgrammaticToolset script can report stale errors — recompile in a fresh call before trusting the failure. `read_graph_dsl` silently omits the bodies of Enhanced-Input event nodes (events print with empty bodies even when fully wired) — inspect those chains with `find_nodes` + `get_connected_subgraph` instead, and don't write such a graph back from its DSL read. Variable accessor type ids are inconsistent across variable age: newly added vars are `Variables|Default|Get<Name>` with the bool `b` prefix DROPPED (`bCrossingActive` → `GetCrossingActive`), while some older vars read back as `|Getb<Name>` — always confirm with `find_node_types` before writing. A node that targets `self` implicitly (e.g. `SetActorLocationAndRotation` on the executing actor) binds its first positional arg to `self` when written via DSL — use keyword args (`:NewLocation`, `:NewRotation`).
- **UMG quirks**: widget templates ship with disabled "ghost" `Tick`/`Construct` event nodes — `add_event` returns them and wiring compiles but generates nothing; even a re-created widget Tick may never fire. Reliable pattern: delete the ghost `Construct`, `add_event` a fresh one, and drive updates with a looping `SetTimerByFunctionName` instead of widget Tick. `CreateWidget` must have `OwningPlayer` wired (pass controller `self`) or `AddToPlayerScreen` silently no-ops. Widget component variables are `Variables|<WidgetName>|Get…`. `ProgressBar` set-percent pin is `Percent`. If a ProgrammaticToolset script errors mid-way, explicitly re-run its remaining steps (e.g. a set-default that never executed). `ObjectTools.set_properties` on runtime/PIE instances only works for **instance-editable** properties (non-editable BP vars read fine but silently refuse writes) — flip `set_variable_instance_editable` first when a test lever is needed. Physics state reads live in `bodyInstance` (e.g. `bodyInstance.bSimulatePhysics`), not on the component. try/except inside ProgrammaticToolset scripts does not reliably catch execute_tool errors — structure scripts so an early failure loses no evidence.
- **UserDefinedStruct/Enum assets cannot be created via MCP** — that is a manual editor step for the human.
- `CaptureViewport` with a manual transform is unreliable during PIE; verify changes by reading graphs/properties back, not screenshots. `CaptureEditorImage` works during PIE but fails if the editor window is not visible on the desktop.
- **Runtime PIE inspection works via MCP**: `SceneTools.find_actors` sees the PIE world (`UEDPIE_0_` refPaths), and `ProgrammaticToolset` scripts may use `time.sleep` to sample moving state across several seconds — the strongest available validation short of a human pass. `Controller`, `ControlRotation`, and `ViewTarget` are not readable via `get_properties`; prove view-target/possession indirectly (camera-manager transform comparison, observed movement). The PIE world advances in REAL TIME between MCP calls — authored AI (e.g. Vanguard strikes) keeps acting on the idle player while you deliberate, so long test sessions drift state (the player can be KO'd between calls); read health/flags at each step and restart PIE for clean phases. Real input CAN be injected: `SlateInspectorToolset.Click` on the editor window (ref from a root `Snapshot`) lands in the PIE viewport as game LMB (fires `IA_Attack`), and `PressKey \"SpaceBar\"` reaches Enhanced Input for a real jump — but only while the PIE viewport holds keyboard focus (re-click the viewport to restore focus; verify the effect, e.g. Z rising, before trusting a key press). Compiling a Blueprint while PIE is running reinstances its actors and silently kills Slate-injected input for the rest of that session even after re-focusing — restart PIE after any mid-session compile before trusting input-driven tests. Runtime instance writes via `set_properties` worked on the attack driver's tuning floats (e.g. `attackDecisionChance` 0 as a temporary test lever; PIE restart restores CDO values).
- **In-memory level instances do not re-sync edited class defaults** during the same editor session (mild form of the stale-instance gotcha): pair any CDO fix with a runtime enforcement or expect it to apply only after reload.

## Architecture and current state

- **Player**: `/Game/ThirdPerson/Blueprints/BP_ThirdPersonCharacter` (Quinn mesh + `ABP_Unarmed`). Attack input `IA_Attack` (LMB, mapped in `/Game/Input/IMC_Default`) plays `MM_Attack_01` via `PlaySlotAnimationAsDynamicMontage` on `DefaultSlot` — no Montage assets are authored; slot-based dynamic montages are the pattern. Hit detection is a delayed `SphereOverlapActors` → native `ApplyDamage`.
- **Enemy proxy**: `/Game/Variant_Combat/Blueprints/BP_VanguardProxy` (Manny mesh, same `ABP_Unarmed`). Handles `ReceiveAnyDamage` → health decrement, `NS_Damage` VFX, camera shake, hit-react montage, and a screen-space `WidgetComponent` health bar (`UI_LifeBar`) initialized via an `EnsureHealthBarWidget` function — never `AddToViewport`. Auto-possessed by the stock AIController (`AutoPossessAI=PlacedInWorld`), which is what lets external Blueprints drive it with `AddMovementInput`; `bUseControllerRotationYaw` is deliberately false (class default + runtime enforcement) so external facing writes are not overridden.
- **Vanguard duel movement**: `/Game/AscendantImpact/Duel/BP_VanguardDuelMover` — runtime-spawned by the PlayerController (gated by `bEnableVanguardMover`, default true, nested inside the duel-camera gate). Movement-only: preferred-range band with hysteresis (advance/hold/retreat), interval-based depth wander, hit-react movement pause via `IsAnyMontagePlaying`, min-axis-separation + lane clamps. Never attacks. Since milestone 14 (blackboard §22) the P1-left/P2-right rule is **dynamic side ownership**, owned by the mover: `CurrentSideSign` (+1 = Vanguard right) updates only while grounded/not-crossing with a `SideDeadzone` (20) hysteresis; the player may jump over the Vanguard — while airborne above `CrossingMinRelativeHeight` (50) the fighters mutually `IgnoreActorWhenMoving` (`SetCrossingCollisionEnabled`), and on landing collision is restored FIRST, then side re-evaluated (order is load-bearing), with any overlap resolved by pushing the Vanguard (never the player). `BP_DuelKnockoutCoordinator.StopMover` clears crossing state before disabling the mover tick. Player jump: CharMoveComp `JumpZVelocity` 820 / `GravityScale` 1.9 / `AirControl` 0.35 (milestone 15 retune from 690/1.25; apex ≈180 cm rise, airtime ≈0.9 s — still clears the Vanguard capsule top at 176 cm). The camera rig owns facing (mutual `FindLookAtRotation`, side-agnostic) with a `FacingUpdateMinDistance` (30) guard against overhead look-at jitter; camera side/arena framing is fixed (`CameraSideSign`) and cannot flip on side swaps. The attack driver's `TryStartAttack` is side-agnostic (abs-separation range gate; both attacks aim via actor forward vectors). Tuning on its class defaults; see blackboard §12 (current values per §15: jog 300 cm/s, preferred distance 180, min axis separation 78 = capsule radii 35+34 plus margin, retreat at 0.5 input scale). Its `ApplyConstraints` is the **single authority for all fighter position constraints**, including the §14 arena bounds (`CombatAxisMin/Max` ±650) — extend it there rather than adding new clamp systems. Camera framing is coupled to those bounds: max separation 1300 requires the rig's `DistancePerSeparation` 0.8 / `MaxCameraDistance` 1500 (half-width ≈ distance × 0.52 at FOV 55) — retune both together.
- **Duel test arena**: `/Game/AscendantImpact/Maps/Lvl_DuelGraybox` — flat-ground duplicate of `Lvl_ThirdPerson` with the central raised platform/ramps removed and both spawns at floor level; made for camera/locomotion evaluation (blackboard §13). The project default map is still `Lvl_ThirdPerson`.
- **Vanguard locomotion**: the Vanguard's mesh runs `/Game/AscendantImpact/Animation/Vanguard/ABP_VanguardLocomotion` — a duplicate of `ABP_Unarmed` whose only logic change is `ShouldMove = GroundSpeed > 3` (speed-only) plus a MovementComponent validity guard; the shared player `ABP_Unarmed` is untouched. The template's `BS_Idle_Walk_Run` is already a full 8-direction × speed blendspace, and `ABP_Unarmed` computes unclamped `Direction` when `bOrientRotationToMovement` is false — directional locomotion needs no new animation assets. Gotchas: the shared ABP's `ShouldMove` acceleration term idles AI-driven characters mid-slide during braking; DSL rewrites of ABP event graphs replace null-tolerant PropertyAccess nodes with hard reads (guard with IsValid or Accessed-None spams from editor preview instances); `save_assets([])` may incidentally resave logically-unchanged shared assets (verify by graph readback, restore from git).
- **Knockout / fight-end**: `/Game/AscendantImpact/Duel/BP_DuelKnockoutCoordinator` — sixth-spawned runtime actor (gated by `bEnableKnockout`, default true). One-shot per fighter at health ≤ 0: cancels the attack driver + disables driver/mover ticks, `DisableMovement` on the loser (player also gets `bIsAttacking=true` to block punches), plays `MM_Death_Front_01`, then ragdolls after `RagdollDelay` 1.4 s (capsule NoCollision + mesh Ragdoll profile + simulate) so the fighter stays down and can take no further hits. Camera + HUD keep running. Selected and scoped by the Assignment 5 goal agent (fight-game `assignment-05/`); see blackboard §18.
- **Vanguard basic strike (graybox prototype, NOT Attack A)**: `/Game/AscendantImpact/Duel/BP_VanguardBasicAttackDriver` — fourth runtime-spawned actor in the controller chain (gated by `bEnableVanguardBasicAttack`). Int-state flow idle/windup/strike/recovery, TextRender "!" telegraph, one class-filtered `SphereOverlapActors` impact per strike (`MM_Attack_02` dynamic montage), cooldowns 2.5–4 s, windup cancel on Vanguard hit-react. Coordinates with the mover only via `SetExternalMovementLocked` (locked = no inputs/decisions, constraints still enforced). The **attack range gate must use combat-axis separation and cover the mover's full hold band** (preferred+deadzone hysteresis, currently ≤225) or the Vanguard can hold legally out of its own attack range and never strike; impact reach = offset+radius+player capsule. Player has a minimal prototype damage receiver (`MaxHealth`/`CurrentHealth`, `HandleDamage`, hit-react + `BP_CameraShake_Hit_Player`, floor at 0, no death). See blackboard §16.
- **Attack data (PAUSED)**: the `S_VanguardAttackDef` struct / `DT_VanguardAttacks` DataTable route under `/Game/AscendantImpact/Data/` is on hold — do not continue it until the human unpauses it. - **Feedback assets** live under `/Game/Variant_Combat/` (`UI_LifeBar`, `NS_Damage`, `BP_CameraShake_Hit_*`).
- **Not yet built (gated)**: Vanguard AI (`BT_CrimsonVanguard`, `BB_CrimsonVanguard`, AI controller), Impact Windows, Ascension Meter, dodge/counter, death-at-zero-health.
